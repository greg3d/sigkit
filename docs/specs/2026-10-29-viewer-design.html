sigkit viewer — design spec

2026-10-29. Status: accepted after a grilling session. Vocabulary: GLOSSARY.md. Tickets: .scratch/viewer/issues/.

Problem Statement

I record raw sensor signals from phones (an Android and an iPhone to start) and I have old raw files from past work. I need to look at them honestly: many channels at different rates, on different clocks, in files that run for an hour at hundreds of hertz, with dropped samples and clocks that drift against each other.

Every viewer I have used for this was either self-written and crashed or crawled on long files, or a general plotting tool that averages samples away on zoom-out, hides gaps, puts grid lines on values like 0.34245, and has no way to stretch one signal against another to see whether two clocks agree. Aligning two devices' recordings today means scripting, and the result is never persisted next to the data.

Solution

sigkit-viewer is a desktop app that opens recordings as they are and shows the truth at every zoom: min/max candles instead of averages, gaps as gaps, and a residual channel that makes jitter, dropped samples and clock drift visible as shapes. Signals are manipulated directly on the plot: drag to shift, stretch to correct a rate, drag across to offset, stretch across to scale. The corrections and calibrations are saved into the recording's header automatically, never into the raw bytes. Two recordings open side by side in one coordinate system. There is no file-size limit. Legacy raw files are imported through a sheet with a live preview. A fixed-rate export writes a clean, uniformly sampled recording for downstream tools such as the filter.

The feel is scientific inside and iPhone outside: the plot is the app, gestures first, everything animated, nothing modal, nothing hidden.

User Stories

  1. As a signal analyst, I want to open a .sigrec recording by double-click, drag-and-drop or command line, so that looking at data costs nothing.
  2. As a signal analyst, I want every channel drawn as min/max candles when a pixel covers many samples, so that spikes and dropouts are never averaged away.
  3. As a signal analyst, I want to open an hour of 500 Hz data on thirty channels and pan and zoom at 60 fps, so that long recordings are as usable as short ones.
  4. As a signal analyst, I want recordings larger than my RAM to open and page in as I scroll, so that there is no size at which the tool gives up.
  5. As a signal analyst, I want the second open of a recording to be instant, so that re-opening is not punished with a rebuild.
  6. As a signal analyst, I want grid lines only at 1-2-5 multiples on both axes, with the time axis switching between ms, s and min on its own, so that I can read values off the grid.
  7. As a signal analyst, I want time to run vertically by default with channels side by side, so that many parallel channels fit on one screen, and I want to switch to horizontal with one button.
  8. As a signal analyst, I want pinch to zoom time around the cursor and Shift+pinch to zoom values, so that zooming is a gesture and not a toolbar trip.
  9. As a signal analyst, I want two-finger scroll to pan both axes with inertia, so that moving through a recording feels physical.
  10. As a signal analyst, I want double-click on the plot to autoscale values to the visible window, double-click on a channel's legend to autoscale to the whole signal, and a Box mode to autoscale to a rectangle I draw, so that I never adjust an axis by hand.
  11. As a signal analyst, I want zoom and autoscale to animate briefly, so that I keep my bearings when the view changes.
  12. As a signal analyst, I want each panel to have one value axis, and channels dropped on the same panel to share it, so that overlaid signals are compared in one coordinate system.
  13. As a signal analyst, I want each channel in its own panel to keep its own view scale, so that a tiny signal next to a large one is still readable.
  14. As a signal analyst, I want a sidebar tree of recordings, streams and channels, so that I can see what is in a file before plotting it.
  15. As a signal analyst, I want to drag a channel from the tree onto a panel to overlay it, between panels to create a new one, and back to the tree to remove it, so that layout is direct manipulation.
  16. As a signal analyst, I want to drop a second recording on the window and see it appear in the tree next to the first, so that comparing two devices starts with a gesture.
  17. As a signal analyst, I want a cursor line through all panels showing each channel's nearest sample value and, for timestamped streams, that sample's stamp, so that I read real samples and not interpolations.
  18. As a signal analyst, I want the time axis in seconds from the recording's zero, and the cursor to also show UTC when the recording has an anchor, so that I can relate a moment to the wall clock without the axis being cluttered.
  19. As a signal analyst, I want to see a timestamped stream's residual against its nominal rate as a virtual channel under the stream, so that clock drift shows as a slope and dropped samples as steps.
  20. As a signal analyst, I want the fitted rate shown as a number and in ppm from nominal, with a toggle that subtracts the fit from the residual, so that I can separate drift from jitter.
  21. As a signal analyst, I want gaps in a timestamped stream to break the line at every zoom level, so that missing data is never drawn as a straight line.
  22. As a signal analyst, I want an Align mode where I grab the active stream on the plot and drag it along time to shift it, so that aligning two recordings is a drag.
  23. As a signal analyst, I want Shift+drag along time in Align to stretch the stream about the point under the cursor, so that I can correct a rate while watching two signals fall into phase.
  24. As a signal analyst, I want drag across values to offset a channel and Shift+drag across to scale it about the cursor, so that level mismatches between sensors are fixed with the same gesture.
  25. As a signal analyst, I want numeric fields for shift, k (also shown as corrected rate and ppm), gain and offset next to the plot, with arrow keys nudging by one pixel and Shift+arrow by ten, so that I can be precise after being fast.
  26. As a signal analyst, I want Align to have no snapping, so that the tool never decides where my signal belongs.
  27. As a signal analyst, I want every calibration and correction saved into the recording's header on each change, with Cmd+Z undo for the session, so that I never lose an alignment and never press Save.
  28. As a signal analyst, I want the raw column bytes of a recording never to change, so that I can always get back to what the sensor said.
  29. As a signal analyst, I want to save and reopen a workspace: which recordings are open, the panels, orientation, view ranges and mode, so that a comparison I set up survives a restart.
  30. As a signal analyst, I want to drop a legacy raw file with no header on the window and get a sheet where I set dtype, byte order, header offset, channel count and rate while a preview re-renders on every change, so that importing old data takes seconds.
  31. As a signal analyst, I want the import sheet to guess dtype by trying plausible decodings, so that the common case is confirm-and-go.
  32. As a signal analyst, I want import to write a header beside the raw file without copying data, so that import is cheap and reversible.
  33. As a signal analyst, I want an explicit export of a timestamped stream to a new fixed-rate recording, with the rate fitted by least squares and gaps written as NaN, so that downstream tools get uniform arrays and still see the holes.
  34. As a signal analyst, I want the mode switch as a segment control at the bottom and the keys 1, 2, 3 as accelerators, so that modes are visible and fast.
  35. As a signal analyst, I want the app to follow the system light/dark theme, use a clean sans-serif, thin antialiased lines and a muted grid, so that it looks like something I want to keep open.
  36. As a signal analyst, I want no modal dialogs, no hidden gestures, no sounds and no onboarding, so that the tool stays out of my way.
  37. As a developer of the toolkit, I want a command-line generator of synthetic recordings with known jitter, drops and ppm drift, so that every feature can be verified against a known truth before any phone logger exists.
  38. As a developer of the toolkit, I want a command-line inspector that prints a recording's streams, channels, counts and fitted rates, so that I can check a file without opening the viewer.
  39. As a developer of the toolkit, I want the recording format and the pyramid in a crate separate from the viewer, so that the logger and the filter reuse them.

Implementation Decisions

Recording format (.sigrec)

  • A recording is a directory named <name>.sigrec with header.json and one planar little-endian column file per channel. A timestamped stream adds one time column. Column files are named <stream>.<channel>.bin and <stream>.t.bin.
  • The unit of storage is the stream: channels sharing one time column (timestamped) or one rate (fixed-rate). A vector sensor is one stream; a single channel is a stream of one.
  • Allowed dtypes: f32, f64, i16, i32, i64. Time columns are i64 in the stream's clock domain unit.
  • Per stream: id, kind, clock domain and unit, nominal rate, rate (fixed-rate only), time correction k and shift, optional UTC anchor, channels, free-text notes. Per channel: id, dtype, unit, gain, offset.
  • Raw column bytes are never rewritten by the viewer. Only header.json is rewritten, atomically (write to a temp file, rename). Unknown header fields are preserved on rewrite.
  • Column lengths are validated on open: every column of a stream must hold the same number of samples. A mismatch is an error, not a silent truncation.
  • A .cache/ directory inside the recording holds the pyramid levels. It is regenerable, versioned, and ignored by git.
  • The header reserves an expressions array for per-element expression channels (v2). Resampling is not an expression; it is the fixed-rate export.
  • MCAP is not the storage format. An MCAP export may come later.

Header shape (decision-encoding, not a schema file):

{
  "sigrec": 1,
  "name": "pixel7-drive",
  "created": "2026-10-29T12:00:00Z",
  "source": { "device": "Pixel 7", "os": "Android 15", "app": "sigkit-logger 0.1" },
  "streams": [
    {
      "id": "accel",
      "kind": "timestamped",
      "time": { "domain": "android.elapsedRealtimeNanos", "unit": "ns" },
      "rate_nominal_hz": 416.0,
      "time_correction": { "k": 1.0, "shift_s": 0.0 },
      "utc_anchor": { "mono": 123456789012, "utc_ns": 1761739200000000000 },
      "channels": [
        { "id": "x", "dtype": "f32", "unit": "m/s^2", "gain": 1.0, "offset": 0.0 },
        { "id": "y", "dtype": "f32", "unit": "m/s^2", "gain": 1.0, "offset": 0.0 },
        { "id": "z", "dtype": "f32", "unit": "m/s^2", "gain": 1.0, "offset": 0.0 }
      ],
      "notes": ""
    },
    {
      "id": "legacy",
      "kind": "fixed_rate",
      "rate_hz": 100.0,
      "time_correction": { "k": 1.0, "shift_s": 0.0 },
      "channels": [ { "id": "ch0", "dtype": "i16", "unit": "", "gain": 0.001, "offset": 0.0 } ]
    }
  ],
  "expressions": []
}

Time

  • The per-sample stamp is the truth; any rate is derived. Delivery rate and batching are irrelevant; only the sensor hub's stamps matter.
  • Clock domains are converted on read into seconds from the recording's zero. Stamps stay raw on disk.
  • Display time of a stream is k · t + shift, applied identically to timestamped and fixed-rate streams.
  • The axis shows seconds from the recording's zero with 1-2-5 ticks that switch between ms, s and min. Each recording has its own zero; shift aligns recordings. UTC appears only in the cursor readout, when the recording carries an anchor.
  • The fitted rate of a timestamped stream is the least-squares slope of stamp against index. The residual channel is t_i − (i / f + t0) with f = nominal rate by default and a toggle to use the fitted rate instead. The fitted rate is shown as a number and as ppm from nominal.
  • Automatic alignment of two devices by GPS time is out of scope for the viewer; the logger still records UTC anchor pairs because they cannot be recorded retroactively.

Rendering and memory

  • Candle rendering: a pixel along time that covers many samples is drawn from the min and the max of those samples. Never an average.
  • The pyramid is built per channel on first open and cached. It is binned by time, not by index: the base bin is 64 nominal intervals; each level above merges two bins. Empty bins are gaps and break the line at every level. The pyramid costs about a quarter of a byte per sample.
  • Below the base level the widget reads raw samples for the viewport straight from the memory-mapped column. For a timestamped stream the viewport's sample range is found by binary search over the monotonic time column. The OS, not the app, decides which pages stay resident.
  • No file-size limit and no scratch files. A recording larger than RAM pages in on untouched regions.
  • The frame draws two vertices per pixel along time per channel plus raw points when zoomed in. No allocation in the frame loop.
  • Rendering goes through egui on the wgpu backend. The plot is a custom widget on the egui painter, not egui_plot.

Plot widget and orientation

  • The widget lives in along-time and across-value coordinates, never x and y. Orientation is a workspace setting that maps them to the screen: vertical (time top to bottom, panels left to right) is the default; horizontal is one toggle away. Every gesture and Align operation is defined in the widget's own terms so switching orientation reassigns nothing.
  • Grid: 1-2-5 ticks on both axes. Time ticks adapt their unit.
  • Panels: one value axis per panel; channels on the same panel overlay in one coordinate system. A channel alone in a panel keeps its own view scale.

Interaction

  • Modes: Pan (default), Align, Box. A segment control at the bottom; keys 1, 2, 3 are accelerators.
  • Pan: pinch zooms along time around the cursor; Shift+pinch zooms across value around the cursor; two-finger scroll pans both axes with inertia.
  • Autoscale: A fits the visible window, Shift+A fits the whole signal, double-click on the plot fits visible, double-click on a legend fits the whole signal, releasing a Box rectangle fits to it. Zoom and autoscale animate over about 150 ms with easing.
  • Align: click a legend to make a stream active, then drag it directly on the plot. Along time: drag = shift, Shift+drag = k anchored at the point under the cursor. Across value: drag = offset, Shift+drag = gain anchored at the cursor. Numeric fields for shift, k (shown also as corrected rate and ppm), gain and offset sit next to the plot. Arrow keys nudge by one pixel, Shift+arrow by ten. No snapping.
  • Cursor: a line through all panels showing each channel's nearest-sample value and, for timestamped streams, the sample's stamp. No interpolation in the readout.
  • Sidebar: a tree of recordings → streams → channels, with the residual as a virtual channel under each timestamped stream. Drag a channel onto a panel to overlay, between panels to create one, back to the tree to remove. Drop a second recording on the window to add it.

Persistence

  • Header edits (calibration, corrections) autosave on every change. Undo (Cmd+Z) covers the session's header edits.
  • The workspace (.sigws.json) holds what belongs to no single recording: open recordings, panels and their channels, orientation, view ranges, mode. It is saved explicitly.
{
  "sigws": 1,
  "recordings": ["pixel7-drive.sigrec", "iphone-drive.sigrec"],
  "orientation": "vertical",
  "mode": "pan",
  "view": { "time_from_s": 12.0, "time_to_s": 48.0 },
  "panels": [
    { "channels": [ { "recording": 0, "stream": "accel", "channel": "z" },
                    { "recording": 1, "stream": "accel", "channel": "z" } ],
      "value_from": -12.0, "value_to": 12.0 },
    { "channels": [ { "recording": 0, "stream": "accel", "channel": "residual" } ] }
  ]
}

Import of legacy raw files

  • Dropping a file that is not a recording opens a sheet with: dtype, byte order, header offset in bytes, channel count for interleaved data, rate, gain and offset. The preview re-renders on every change.
  • The initial dtype is guessed by decoding a prefix as each plausible dtype and scoring plausibility (finite, bounded, not dominated by outliers).
  • Confirming writes a header.json beside the file as a fixed-rate stream; the data is not copied.
  • The stream reads the file in place through a raw block: { "file": "bench.dat", "offset_bytes": 512, "byte_order": "big" }. Its channels are interleaved in header order, one element each per frame; bytes after the last whole frame are left out. This is the one exception to one planar little-endian column file per channel. One raw file per folder, since the header is always header.json.

Fixed-rate export

  • An explicit command on a timestamped stream. The target rate defaults to the fitted rate, editable in the export sheet.
  • Linear interpolation onto the uniform grid. A gap longer than two nominal intervals is written as NaN, not interpolated across.
  • The output is a new recording next to the source, with the residual exported beside it as a channel.

Look and feel

  • Follows the system theme. Inter for text. Thin antialiased lines, muted grid, a fixed channel palette.
  • Anything needing input is a sheet or a sidebar with a live preview. No modal dialogs, no hidden gestures, no sounds, no onboarding.

Stack and repository

  • Rust stable, egui with the wgpu backend, a custom plot widget. Cargo workspace: sigkit-format (format, pyramid, residual, resampling, rate fit, synthetic generator), sigkit-viewer, a sigkit CLI, later sigkit-ekf. Phone loggers under loggers/, specified separately.
  • The synthetic generator produces recordings with known truth: fixed-rate sine plus noise; timestamped with configurable jitter, dropped samples and ppm drift; a pair preset that writes two recordings of the same physical signal on two drifting clocks with a shift. Every viewer feature is verified against these before any phone logger exists.

Testing Decisions

  • A good test exercises external behaviour at a seam and never implementation details. There is no CI and no coverage target.
  • Seams, all in sigkit-format and all pure functions over columns: read/write round-trip of a recording (including unknown header fields and length validation); pyramid building (a bin's min/max equals the brute-force min/max of the samples it covers, empty bins are marked); least-squares rate fit and residual (recover the ppm drift and the drop steps that the generator injected); resampling (gap → NaN, interpolation exact on a linear signal); dtype guessing on generator output.
  • The viewer UI is not unit-tested. It is verified by hand on generator recordings and, later, on real phone recordings. Each ticket's acceptance criteria say what to look at.
  • Prior art: none, this is a new repository. Tests are plain Rust #[test] functions and integration tests under tests/ using a temporary directory.

Out of Scope

  • Live streaming from a phone (the format is append-friendly for it; later).
  • Automatic alignment of two recordings by GPS time.
  • Expression channels (schema slot reserved).
  • Map view, FFT, Allan variance, MCAP export.
  • Snapping in Align, onboarding, tooltips, sounds.
  • Packaging and polish for Windows and Linux. The code is portable; only macOS is verified.
  • The phone loggers and the filter. They get their own specs.

Further Notes

  • The Rust toolchain is not installed on the development Mac at the time of writing. Install via rustup before ticket 01.
  • The glossary is the vocabulary for tickets, code identifiers and UI labels. New terms go there first.
  • Memory is bounded by the pyramid and the resident pages the viewport touched; there is deliberately no cap and no scratch-file layer.
